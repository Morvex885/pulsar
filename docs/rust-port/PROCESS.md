# Регламент агента

Правила для агентов, берущих пакеты порта. Спеки пакетов — `wp/WP-XX.md`, статус — `PROGRESS.md`, контракты — `ARCHITECTURE.md`, станции — `STATIONS.md`.

1. **Выбор.** Берётся пакет со статусом `свободен`, у которого все пакеты из «Старт после» в статусе `влит`.
2. **Захват.** Ветка вида `wp/WP-XX` от `origin/rust`, в Orca-worktree или через `git worktree add`.
   - В PROGRESS.md правится только своя строка: `в работе`, исполнитель.
   - Коммит `WP-XX: claim`, затем `git push origin HEAD:rust`.
   - Если push отклонён (non-fast-forward): `git fetch origin && git rebase origin/rust`. Если строку уже занял другой агент — откатить свой захват и выбрать другой пакет. Иначе push повторить.
3. **Работа.**
   - Прочитать спеку пакета, ARCHITECTURE.md и весь перечисленный C++-эталон.
   - Писать только в крейт(ы) своего пакета и в перечисленные документы.
   - Удалить C++-файлы из списка «Удалить в этом пакете».
   - Чужие влитые крейты разрешено менять только для исправления найденного бага: отдельный коммит `WP-XX: fix <crate>: …` с описанием в отчёте ревью.
   - Если меняется контракт из ARCHITECTURE.md, в том же коммите правятся ARCHITECTURE.md и спеки зависимых пакетов, а в «Заметки» PROGRESS.md пишется строка.
4. **Эталон C++** — тег `rust-port-base`, а не `main`: в ветке файлы удаляются, `main` может уйти вперёд.
   - Читать: `git show rust-port-base:satellite/src/<путь>`; пути вне `satellite/src/` (`satellite/tools/…`, `satellite/third_party/…`) — полностью: `git show rust-port-base:satellite/tools/<файл>`.
   - Эталонные C++-утилиты собираются в своём detached worktree: `git worktree add --detach ../pulsar-ref-WP-XX rust-port-base`, затем `make -C ../pulsar-ref-WP-XX/satellite ZIG=<zig 0.14.1> ARCH=<arch> build/<arch>/tools/<tool>`. По одному worktree на пакет, имена не пересекаются.
   - Golden-векторы для чистых функций получаются так: функция C++ компилируется на host (`zig c++ -std=c++20` + маленький одноразовый harness), её вывод фиксируется в `crates/<крейт>/tests/golden/`. Генератор не коммитится, а в сообщении коммита пишется, как получены данные.
5. **Локальная проверка.** `make -C satellite check` и `make -C satellite -j"$(nproc)" ARCH=aarch64 binary tools`, то же для `ARCH=armhf`. Если пакет первым использует workspace-зависимость — один раз `cargo check` без `--locked` в `satellite/` и закоммитить Cargo.lock.
6. **Станции.** Проверка по STATIONS.md и разделу «Проверка на станциях» спеки. Команды и ключевые строки вывода записываются в отчёт ревью.
   - Станция занята чужим непросроченным lock: повторять попытку каждые 5 минут.
   - Ожидание дольше 3 часов или станция недоступна (ssh не отвечает) — статус `заблокирован: …`, работа останавливается, владельцу сообщается.
   - Влить пакет без проверки на станциях, которые требует спека, нельзя.
7. **Ревью.** Минимум два независимых агента-ревьюера.
   - Ревьюер — не исполнитель: свежий контекст, без доступа к переписке исполнителя. Подойдёт агент `reviewer`, запущенный исполнителем или оркестратором, либо отдельная Orca-сессия.
   - Ревьюер A — баги и паритет поведения с C++-эталоном.
   - Ревьюер B — архитектура и соответствие ARCHITECTURE.md и контрактам, unsafe/FFI (layout, время жизни, потоки), конкурентность и отмена, ошибки и утечки ресурсов, нагрузка на Lite 2 (RSS, CPU).
   - Для пакетов с FFI (WP-04, WP-05, WP-06) допускается третий ревьюер только по unsafe.
   - Исполнитель исправляет все блокирующие и важные замечания или письменно обосновывает отказ. После исправлений ревьюеры смотрят дельту. Цикл повторяется, пока у всех вердикт не станет «можно вливать».
   - Отчёт сохраняется в `docs/rust-port/reviews/WP-XX.md`.
   - Шаблон задания ревьюеру:
     ```
     Ты независимый ревьюер пакета WP-XX порта pulsar на Rust. Репозиторий: <путь>, ветка wp/WP-XX, база origin/rust.
     Прочитай: docs/rust-port/wp/WP-XX.md, docs/rust-port/ARCHITECTURE.md, AGENTS.md, diff `git diff origin/rust...HEAD`,
     C++-эталон из раздела «Эталон C++» спеки (в ветке файлы удалены — читай через `git show rust-port-base:satellite/src/<путь>`, пути вне satellite/src/ — полностью, например `rust-port-base:satellite/tools/<файл>`).
     Фокус: <A: баги и расхождения поведения с C++ | B: архитектура/контракты/unsafe/конкурентность/ресурсы>.
     Ничего не правь. Верни список замечаний: [блокирующее|важное|мелкое] файл:строка — проблема — почему — как исправить.
     В конце вердикт: «можно вливать» или «нельзя вливать».
     ```
8. **Влитие.**
   - В PROGRESS.md своя строка: `влит`, «Ревью» — ссылка, Midi и Lite 2 — результат.
   - `git fetch origin && git rebase origin/rust`. Конфликты:
     - PROGRESS.md — взять версию `origin/rust` и заново применить правку своей строки;
     - `satellite/Cargo.lock` — `git checkout origin/rust -- satellite/Cargo.lock`, затем `cargo metadata --format-version 1 >/dev/null` в `satellite/` (добавит недостающие записи без обновления остальных);
     - корневой `satellite/Cargo.toml` — объединить обе правки.
     - После каждого разрешения — `git add <файлы> && git rebase --continue`.
   - Свести работу в один коммит поверх `origin/rust`: `git reset --soft origin/rust && git commit -m "WP-XX: <название пакета>"`. Коммит захвата уже в `rust` и не трогается.
   - Если после rebase изменился Rust-код из `origin/rust`, повторить п. 5.
   - `git push origin HEAD:rust`. При non-fast-forward — повторить с `git fetch`.
   - Затем `gh run watch` по запуску CI на `rust`. Если CI красный — исправление вперёд отдельным коммитом `WP-XX: fix CI: …` сразу же.
