# Ревью WP-01 — ESPHome: транспорт, Noise, клиенты, voice-владелец

- Пакет: WP-01
- Коммит-база: `3b18614` (захват WP-01 поверх `origin/rust` = `6ad5244`); при влитии перенесено на `origin/rust` с влитыми WP-07 и WP-11
- Ревьюеры: A — «rv01a» (баги и паритет с C++), B — «rv01b» (архитектура, контракты, unsafe, конкурентность, ресурсы)
- Раунды: 1 — по коммиту `d3aebb5`; 2 — по дельте `d3aebb5..f060936`; 3 — по дельте `f060936..4b5b00f`. Мелкие правки раунда 3 внесены в итоговый коммит.

## Блокирующие

Нет.

## Важные

- [важное] `crates/pulsar-esphome/src/server.rs`, ветка accept (B, раунд 1) — на `Accept(Err)` (EMFILE/ENFILE/ENOBUFS/ENOMEM) tokio `poll_accept` сохраняет готовность, и `biased`-select крутится на 100 % CPU с потоком warn, клиентский ввод-вывод голодает — исправлено в `f060936`: одна запись в лог на эпизод, ветка accept выключается предусловием `select!` и включается одноразовым таймером через 500 мс; очередь соединений забирается за одно пробуждение (как цикл `accept4` в C++), ограничена backlog listen (4) и бюджетом задачи tokio, accept стоит перед вводом-выводом клиентов. Тест через тестовый шов `FAIL_ACCEPT` на остановленных часах.
- [важное] `server.rs`, `process`/`send_msg` (B, раунд 2) — пакетный flush убрал ограничение backlog 8 МиБ в пределах одного пробуждения: «усиливающие» запросы (повторный Hello; в WP-02 ListEntities/SubscribeStates/DeviceInfo) могли раздуть `wbuf` до десятков МиБ — OOM на Lite 2 — исправлено в `4b5b00f`: внутри пакета flush при backlog ≥ 64 КиБ, разбор прекращается после закрытия клиента; тест `amplified_replies_still_meet_the_backlog_limit`.

## Мелкие

Раунд 1, ревьюер B:
- [мелкое] `key.rs` `load_key` — любая ошибка чтения, кроме отсутствия файла, считалась «нет ключа» — исправлено в `f060936`: только NotFound или пустое содержимое; иначе fail-closed.
- [мелкое] `sys.rs`/`key.rs` — `getrandom` без повтора на EINTR и известный запасной ключ `[0xa5; 32]` — исправлено в `f060936`: повтор на EINTR и дочитывание; при стойком отказе состояние `reject_all` (все Noise-рукопожатия — «Handshake MAC failure»).

## Намеренные отличия от C++

- Геттеры `connected()`/`voice_subscribed()` — по контракту (ARCHITECTURE «Модель исполнения» п.2): итог ввода-вывода приходит событиями.
- Файл ключа, который есть, но не читается (любая ошибка, кроме NotFound), — fail-closed; C++ считал его пустым (plaintext).
- `reject_all`: при стойком отказе `getrandom` все Noise-рукопожатия отклоняются «Handshake MAC failure»; C++ брал известный ключ `[0xa5; 32]`.
- `voice_stale`: после смены voice-владельца `VoiceSendAudio`/`VoiceRequestStop` отбрасываются до следующего `VoiceRequestStart`.
- Accept: вся очередь за одно пробуждение (ограничена backlog и бюджетом tokio), accept раньше ввода-вывода клиентов; на исчерпании ресурсов — пауза 500 мс, лог один раз на эпизод.
- Ответы на один пакет ввода уходят одним flush (ранний flush при 64 КиБ); буферы клиентов сжимаются до 64 КиБ после роста за 256 КиБ.
- Классификация ошибок рукопожатия как в noise-c: усечённое сообщение и нулевой эфемерный ключ — «Handshake error», не «Handshake MAC failure».
- Строки с провода декодируются как UTF-8 с заменой (C++ копировал байты); ключ SetKey берётся сырыми байтами.

## Зависимости

- `snow` — без фич по умолчанию (`use-chacha20poly1305`, `use-sha2`, `use-curve25519`, `use-getrandom`): фича `std` snow 0.10.0 тянет `ring` (не-weak `ring/std`) и неиспользуемые AES-GCM и BLAKE2. До влития WP-11 это ещё и ломало кросс-clippy `make check` (build-скрипт `ring` без C-компилятора цели); после WP-11 кросс-clippy идёт через `cargo-zigbuild`, причина осталась одна — лишний код. ARCHITECTURE.md и «Заметки» PROGRESS.md обновлены.
