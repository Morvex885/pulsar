# Removing Yandex network services from the Mini 2

Research for [issue #5](https://github.com/RisinT96/pulsar/issues/5), 2026-10-31. Pulsar source observations refer to [fd434437d2aa94a1c522df7ea8ae8ed0818d7de8](https://github.com/RisinT96/pulsar/tree/fd434437d2aa94a1c522df7ea8ae8ed0818d7de8). Firmware observations below come from **read-only inspection of this owner's current Mini 2**, not a promise about other firmware. No changes, reboot, network capture, or end-to-end Pulsar test were made.

## Decision and limits

Use a configurable, non-Yandex LAN DNS resolver and an NTP server reachable from the station. Maintain settings under `/data`, retain stock rootfs, and enforce network policy at the router before boot during migration and validation. First establish the actual DHCP and IPv6 DNS inputs and available local time service; Home Assistant being present does **not** imply it provides DNS or NTP. Design and test a persistent, reversible time-service override before deployment. Router filtering gives an independent defense during early boot and recovery; a Yandex domain denylist alone is not proof that every endpoint or hardcoded address is covered. Blocking all unneeded station egress, with explicit exceptions as required, is stronger; do not block LAN connectivity, SSH, ADB, HA, MA, DHCP, DNS, NTP or necessary established connections. IPv4 and IPv6 both need examination.

This is a plan, not proof of total Yandex independence. The project still deliberately loads proprietary local libraries and models from the Yandex firmware. A reasonable definition to validate is no Yandex network traffic, including at boot, DHCP renewal, failure and rollback, while HA and music continue to work. Other Internet access, e.g. Music Assistant sources or GitHub updates, is a separate policy choice.

## Observed DNS behavior

* The station uses `dhcpcd` and Unbound. `/etc/resolv.conf` points to a generated `/tmp` file naming localhost, with `/data/unbound_enabled` present. `/data/unbound.conf.head` contains Yandex DNS forwarders; the generated `/etc/unbound/unbound.conf` also contains DNS servers supplied by the LAN. The system root is a read-only UBIFS mount.
* The firmware's `/lib/dhcpcd/dhcpcd-hooks/21-unbound.conf`, directly inspected on this device, builds the configuration from `/data/unbound.conf.head` if present, otherwise a firmware default, and **appends** servers collected from DHCP and IPv6 router advertisements. It updates the configuration and reloads Unbound when changed. Therefore replacing Yandex entries in the persistent head is a promising firmware-supported seam, but does not control the appended servers; ensure DHCP and IPv6 advertisements contain only approved DNS. The generated file alone is transient and can be replaced on renewal. The [station-network documentation](https://hackalice.me/platform/network/) describes the same hook, but the device observation is the primary evidence for this build.
* Verify exact behavior when no DNS is offered, an interface is removed, DHCP renews, IPv6 changes, and the resolver is unavailable. Preserve a private backup of the existing `/data` header and markers. Do not put private addresses, configs or logs in the repository.

## Observed time behavior and boot ordering

* `chronyd` 3.5 is running, with `/etc/chrony.conf` pointing at Yandex's `ntp.yantp.net`; `/etc/init.d/S49chrony` starts it using that default when `/data/chrony_is_enabled` exists, optionally taking arguments from `/etc/default/chrony`. The latter is on the protected root filesystem. There is no observed `/data` configuration override for chrony analogous to the Unbound hook. The [chrony 3.5 documentation](https://chrony-project.org/doc/3.5/chronyd.html) documents `-f` for an alternate config; a future `/data`-resident service could run the existing daemon with its own config, but ownership, start/stop, retry, fallback and power-cycle behavior still need to be designed and tested. Do not assume the current firmware supports any unverified flag or hook.
* Pulsar's [boot script](https://github.com/RisinT96/pulsar/blob/fd434437d2aa94a1c522df7ea8ae8ed0818d7de8/satellite/deploy/boot.sh) runs after the stock quasar boot script, waits for it, then stops the stock stack. On this device chrony starts earlier still. A change made only in the Pulsar boot script leaves a window in which firmware services may contact Yandex. A late restart of chrony alone cannot satisfy a no-contact-since-power-on requirement.
* [supervise.sh](https://github.com/RisinT96/pulsar/blob/fd434437d2aa94a1c522df7ea8ae8ed0818d7de8/satellite/deploy/supervise.sh) and [ctl.sh](https://github.com/RisinT96/pulsar/blob/fd434437d2aa94a1c522df7ea8ae8ed0818d7de8/satellite/deploy/ctl.sh) intentionally return to the Yandex stack on disable or failed recovery. Treat this as a recovery path that may try to connect externally; enforce the independent network policy during rollback as well. Changing this behavior requires a separately verified recovery design. Preserve SSH and root ADB access and the working binary rollback.
* An HA time synchronization message may help after HA connects, but cannot guarantee an accurate clock while HA is unreachable or before it connects. Confirm correct boot-time timekeeping and timezone separately; accurate time matters for the clock and HTTPS certificate validation.

## Other dependencies and policy

Pulsar's [README limitations](https://github.com/RisinT96/pulsar/blob/fd434437d2aa94a1c522df7ea8ae8ed0818d7de8/README.md) explicitly say firmware DNS and NTP remain. The daemon uses LAN ESPHome and Sendspin services, and wake arbitration/mDNS; see the [architecture](https://github.com/RisinT96/pulsar/blob/fd434437d2aa94a1c522df7ea8ae8ed0818d7de8/docs/architecture.md). Its [updater](https://github.com/RisinT96/pulsar/blob/fd434437d2aa94a1c522df7ea8ae8ed0818d7de8/satellite/crates/pulsar-update/src/updater.rs) contacts GitHub for releases, so a full Internet block disables that update path unless an exception or an offline update procedure is provided. Music sources may have their own network requirements, commonly on the Music Assistant host rather than the speaker. Existing OTA behavior and traffic from firmware processes or local libraries remain unmeasured; stopping `maind` does not establish that every other process is silent.

## Before implementation: acceptance and rollback

1. Inventory DHCPv4 and IPv6 DNS offers, network enforcement capabilities, local resolver and real NTP availability, and obtain a private configuration backup. Define an explicit allow policy that preserves access and local services before changing any policy.
2. Prototype the `/data` DNS-head override on this firmware, validate generated config and resolver behavior across boot, lease renewal, disconnect and IPv6 changes; verify no Yandex resolver is used even on failure. Test the existing daemon's actual alternate-config support and define a supervisor-compatible time-service replacement that survives reboot without touching the rootfs. Independently account for the period before Pulsar starts.
3. Capture DNS, NTP and outbound connections at the network boundary from before power-on through boot, normal voice and music, DHCP renewal, offline/reconnect, crash-loop and explicit recovery. Inspect IPv4/IPv6 and direct connections; do not infer absence from DNS logs alone. A finite observation is evidence for the tested scenarios, not proof that all future firmware paths are silent.
4. Verify clock synchronization to the selected non-Yandex source, HA discovery and voice, TTS URL playback, Sendspin, physical controls, hardware microphone mute, and local controls with HA unavailable. Follow the repository's station test protocol and obtain consent before audio playback.
5. Document a tested out-of-band rollback for DNS, time, network rules and daemon, including how to restore prior `/data` files and service state through root SSH/ADB, without removing root access. Stock recovery may require LAN policy exceptions but need not receive Yandex Internet access.
